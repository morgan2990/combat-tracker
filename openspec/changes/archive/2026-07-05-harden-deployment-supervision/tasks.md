## 3. Migrate services one at a time, in order of increasing risk

Every step below follows the same shape: stop the native process → confirm its port is actually free (`ss -tln`, since the native processes hold these ports and would block the container from binding them) → bring up the Compose service → verify → only then move on.

- [x] 3.1 Migrate `cloudflared` first (stateless, easiest to validate and roll back): stopped the native process, brought up the Compose service, dashboard ingress updated to `http://combatapp:8080`. Verified end-to-end: `https://combat-app.morgan2990.com/` → 200, `/api/me` → 401 (correctly unauthenticated). One learning worth noting for the remaining steps: killing a supervised container's process via `kill <pid>` doesn't stop it — Docker's restart policy immediately restarts it with a new PID. Use `docker stop`/`docker compose stop <service>` instead when a container actually needs to be stopped.
- [x] 3.2 Migrate `minio`: native process was already stopped (by user, while investigating the cloudflared respawn). Hit a rootless-Docker UID remapping issue on first start (host data owned by root, container-root maps to host UID 100000) — fixed by `chown -R 100000:100000` on all three bind-mounted data directories (mongo, minio, typesense) at once to avoid hitting this three times. Container now healthy; verified reachable at the existing `192.168.0.100:9000` endpoint with no storage errors in combatapp's logs.
- [x] 3.3 Migrate `typesense`: native process was already stopped (user, same Portainer cleanup as minio). Container started against `/data/compose/2/typesense-data`, correctly restored its existing snapshot. Found the image ships no `curl`/`wget` (minimal Debian-based image, confirmed via `docker exec`), so the healthcheck was switched to a `bash /dev/tcp` TCP-reachability check instead — now healthy. Verified: document counts match exactly what was live before migration (2,640 items, 14,365 monsters), no errors in combatapp's logs.
- [x] 3.4 Migrate `mongo` last (most critical, most data): native process was already stopped (user, same cleanup). Caught and fixed a real bug before starting it: the compose service was missing the native process's `--auth` flag — since we're pointing at an *existing* database rather than a fresh init, the official image's entrypoint wouldn't have re-added it, which would have started production data completely unauthenticated. Fixed (`command: ["mongod", "--auth", "--bind_ip_all"]`). Verified healthy, `combatapp`'s Go driver reconnected automatically with zero errors, and an authenticated query confirmed all real production data intact (5 users, 8 PCs, 2 rooms, 2 parties, 1 encounter, 7181 monsters, 2640 items).
- [x] 3.5 All four native processes (cloudflared, minio, typesense-server, mongod) are stopped, not removed — binaries remain installed on the Pi for rollback if needed.
